# Phase 0 implementation notes and unresolved gates

Design basis: v4.3.3, inspected in full before implementation. Existing design
and `.clang-format` were preserved. Only Phase 0 capability experiments and build
tooling are implemented; no production state machine, subscriptions manager,
cleanup service, CLI/Web server or UDS recorder protocol is claimed.

## Engineering choices

- C++17 is required with extensions disabled. Main-probe warnings include
  Wall/Wextra/Wpedantic/Wconversion/Wsign-conversion. Vendor code is not reformatted.
- The existing Google-based `.clang-format` is the baseline. `format-cpp.py` adds
  a whitespace-only one-argument-per-line pass because clang-format 14 otherwise
  packs short calls even with bin-packing disabled. Public probe interfaces state
  ownership, failure behavior and concurrency boundaries.
- Four independent submodules are pinned by gitlink. Upstream tags are only the
  initial selection aid. `verify-submodules.sh` rejects wrong URLs, wrong gitlink
  modes/stages, wrong checkouts, dirty/uninitialized dependencies and invalid
  recursive submodules. Isolated fixture tests mutate tracked files, URLs and SHAs.
- `tests/support/` contains experiments, not production headers. Both pool modes
  share fixed Node storage and bounded fallback. A shared state keeps storage alive
  until handles and TLS caches disappear; release never allocates a new TLS cache.
  MessageHandle and BudgetLease have independent lifetimes. A live worker rebuilds
  queues and tokens across 16 generations with the process-level pool retained.
- Root CMake never finds or links the custom fixture package. `run-phase0.sh`
  builds it independently into a test prefix. It sources the package-local setup
  generated by ament, not a nonexistent colcon prefix setup file.
- `payload_binding.hpp` keeps the actual SerializedMessage owner without invoking
  a destructive Writer overload. It copies only the small C descriptor. Counted
  allocator tests and actual MCAP reads test the ownership assumptions.
- The installed PlotJuggler DataLoadMCAP and ParserROS2 plugins are executed by a
  small Qt harness. Analysis Docker images contain only that harness and installed
  plugins; they have no `/work`, fixture interfaces or generated type support.
  Only two read-only MCAP files are mounted, and the network is disabled. Every
  numeric/string fixture sample is checked, including absolute MCAP log timestamps.
- The retained custom files are produced by a final C++ Writer registration/write
  experiment using `config/mcap.yaml`, after deterministic Python serialization.
  Actual Chunk records confirm LZ4, and clean PlotJuggler parses those C++ outputs.
  Additional retained standard bags prove Schema associations and 100-message counts.
- Docker manifests for official Humble/Jazzy bases are pinned in
  `docker/base-images.json`. Both dcl-based AMD64 builds passed; the official pinned
  Humble and Jazzy AMD64 jobs additionally built and passed all five tests each.
  The first official Jazzy attempt was stopped for disk capacity; its successful
  retry is retained separately rather than overwriting the interruption evidence.
- Workflows never publish and never run external PR code with host IPC/network.
  Local DDS tests explicitly use isolated ROS_DOMAIN_ID values and trusted containers.
- Preview packaging fails closed unless `--phase0-preview` is given. It labels
  itself incomplete and contains only the available native skeleton binary.

## Failures investigated rather than hidden

1. Git HTTPS fetches initially failed intermittently. Retried locally, then checked
   exact gitlinks and clean worktrees. No dependency contents were hand-edited.
2. The first lifetime test expected unique_ptr::reset to destroy the deleter. The
   deleter still owns shared state; replacing/destroying the handle is the correct
   final-owner boundary. The test was corrected, not the ownership guarantee.
3. ament_target_dependencies requires consistent PUBLIC link signatures when
   mixed with target_link_libraries. Both distro builds now compile that path.
4. A non-root Humble container lacked a writable default ROS logging directory.
   Explicit per-test ROS_LOG_DIR fixes the environment without changing `$HOME`.
5. GCC TSan initially aborted at startup with `unexpected memory mapping`.
   Process-local `setarch x86_64 -R` permits execution. Docker's default seccomp
   rejects that personality change, so the trusted sanitizer-only runtime uses
   `--security-opt seccomp=unconfined`. No machine-wide ASLR settings changed.
6. The host's prebuilt Humble stack reports ASan new-delete-type-mismatch through
   rclcpp's allocator adapter/rcutils string-map teardown. A minimal ROS node with
   no pool/queue/binding reproduces it. The separate updated Humble container
   passes the same ASan callback experiments. The host result remains FAIL and is
   not retroactively changed into PASS.
7. Full ROS Humble TSan reports mutex/lock-order diagnostics in prebuilt Fast DDS
   and spdlog paths. A minimal node also reproduces diagnostics. Core pool/queue
   and payload TSan pass, and full Jazzy Executor TSan passes. No suppression,
   sanitizer-disable flag or forced successful exit is used for Humble.

8. Reusing a CMake build tree with another Jazzy SDK image failed to link the
   cached Fast CDR 2.2.7 path. Rebuilding in its original SDK image passed; container
   build trees are tied to the actual dependency tuple, not only the distro name.
   `jazzy-delivery-tests.txt` retains the failed cross-image attempt.
9. New DDS-to-MCAP checks exposed host/container data loss when the container
   participants ran as root. Running the trusted container probes as the host UID
   passed all 100 actual received/written/read-back values in both distros. Distinct
   domains separate the two experiments. Shared-memory permissions are a likely
   cause, not a proven general diagnosis; failed root-run logs are retained.
10. Editing the CI helper while an earlier shell invocation was still running
    interrupted that invocation after its successful Docker image build. The final
    helper passes syntax/ShellCheck; the resulting image's runtime suite was
    executed separately. `official-humble-delivery.txt` retains the interruption.
11. The initial L2 AC-55 helper run against an older Humble image lacked the new
    `rewrite-custom` mode. Rebuilt the image; the helper then passed. Both attempts
    remain recorded; the Jazzy helper passed with its compatible image.

12. Exit-audit inspection found the preview's three Bash entries were 0775,
    inherited from the workspace by copy2. The packager now explicitly sets 0755,
    and the source entry modes were corrected. The replacement preview checks
    exact archive modes, not just executable bits. The earlier preview was moved
    to `build/phase0-delivery-superseded-mode775`; it is not the delivery artifact.

## P1 items and boundaries

- Host Humble ASan baseline failure needs a documented supported dependency tuple;
  updated container ASan success does not validate the older host runtime.
- Both official AMD64 builds passed. Native ARM64 remains unexecuted; AMD64
  results do not establish ARM64 API, ABI or sanitizer behavior.
- The full interactive PlotJuggler UI was not manually exercised; this acceptance
  executes the actual installed loader/parser used by that application.
- Production payload-size distributions, 10×1000 Hz performance, rolling/cleanup,
  complete control protocols and real robot testing belong to later phases.
- Source-identity evidence contains the unchanged baseline SHA **and dirty source
  file hashes**; it is not a clean release commit and must not be labeled one.
- Remaining design-review questions from the prior analysis (runtime protocol,
  capacity, recovery ownership) were not silently rewritten during Phase 0.

## Resuming validation

Use the commands in `phase0_validation_report.md`. Keep failures and versioned
evidence, run native ARM64 jobs, resolve the Humble sanitizer baseline, then obtain
the specified reviewer sign-off. Only after those gates close can Phase 0 exit be
re-evaluated. Switching Pool modes or changing supported capabilities requires the
existing review process, not an automatic code fallback.
