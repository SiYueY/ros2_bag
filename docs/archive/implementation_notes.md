# Implementation notes and unresolved gates

Design basis: v4.3.8. The opening Phase 0 notes below preserve the historical

## Engineering choices

- C++17 is required with extensions disabled. Main-probe warnings include
  Wall/Wextra/Wpedantic/Wconversion/Wsign-conversion. Vendor code is not reformatted.
- The existing Google-based `.clang-format` is the baseline. `format-cpp.py` adds
  a whitespace-only one-argument-per-line pass because clang-format 14 otherwise
  packs short calls even with bin-packing disabled. Public probe interfaces state
  ownership, failure behavior and concurrency boundaries.
- Four independent submodules are pinned by gitlink. Upstream tags are only the
  initial selection aid. `verify-submodules.sh` rejects wrong URLs, wrong gitlink
  modes/stages, wrong checkouts, dirty/uninitialized dependencies and invalid
  recursive submodules. Isolated fixture tests mutate tracked files, URLs and SHAs.
- `tests/support/` contains experiments, not production headers. Both pool modes
  share fixed Node storage and bounded fallback. A shared state keeps storage alive
  until handles and TLS caches disappear; release never allocates a new TLS cache.
  MessageHandle and BudgetLease have independent lifetimes. A live worker rebuilds
  queues and tokens across 16 generations with the process-level pool retained.
- Root CMake never finds or links the custom fixture package. `run-phase0.sh`
  builds it independently into a test prefix. It sources the package-local setup
  generated by ament, not a nonexistent colcon prefix setup file.
- `payload_binding.hpp` keeps the actual SerializedMessage owner without invoking
  a destructive Writer overload. It copies only the small C descriptor. Counted
  allocator tests and actual MCAP reads test the ownership assumptions.
- The installed PlotJuggler DataLoadMCAP and ParserROS2 plugins are executed by a
  small Qt harness. Analysis Docker images contain only that harness and installed
  plugins; they have no `/work`, fixture interfaces or generated type support.
  Only two read-only MCAP files are mounted, and the network is disabled. Every
  numeric/string fixture sample is checked, including absolute MCAP log timestamps.
- The retained custom files are produced by a final C++ Writer registration/write
  experiment using `config/mcap.yaml`, after deterministic Python serialization.
  Actual Chunk records confirm LZ4, and clean PlotJuggler parses those C++ outputs.
  Additional retained standard bags prove Schema associations and 100-message counts.
- Docker manifests for official Humble/Jazzy bases are pinned in
  `docker/base-images.json`. Both dcl-based AMD64 builds passed; the official pinned
  Humble and Jazzy AMD64 jobs additionally built and passed all five tests each.
  The first official Jazzy attempt was stopped for disk capacity; its successful
  retry is retained separately rather than overwriting the interruption evidence.
- Workflows never publish and never run external PR code with host IPC/network.
  Local DDS tests explicitly use isolated ROS_DOMAIN_ID values and trusted containers.
- Preview packaging fails closed unless `--phase0-preview` is given. It remains
  incomplete and is not a V1.0 release artifact.

## Failures investigated rather than hidden

1. Git HTTPS fetches initially failed intermittently. Retried locally, then checked
   exact gitlinks and clean worktrees. No dependency contents were hand-edited.
2. The first lifetime test expected unique_ptr::reset to destroy the deleter. The
   deleter still owns shared state; replacing/destroying the handle is the correct
   final-owner boundary. The test was corrected, not the ownership guarantee.
3. ament_target_dependencies requires consistent PUBLIC link signatures when
   mixed with target_link_libraries. Both distro builds now compile that path.
4. A non-root Humble container lacked a writable default ROS logging directory.
   Explicit per-test ROS_LOG_DIR fixes the environment without changing `$HOME`.
5. GCC TSan initially aborted at startup with `unexpected memory mapping`.
   Process-local `setarch x86_64 -R` permits execution. Docker's default seccomp
   rejects that personality change, so the trusted sanitizer-only runtime uses
   `--security-opt seccomp=unconfined`. No machine-wide ASLR settings changed.
6. The host's prebuilt Humble stack reports ASan new-delete-type-mismatch through
   rclcpp's allocator adapter/rcutils string-map teardown. A minimal ROS node with
   no pool/queue/binding reproduces it. The separate updated Humble container
   passes the same ASan callback experiments. The host result remains FAIL and is
   not retroactively changed into PASS.
7. Full ROS Humble TSan reports mutex/lock-order diagnostics in prebuilt Fast DDS
   and spdlog paths. A minimal node also reproduces diagnostics. Core pool/queue
   and payload TSan pass, and full Jazzy Executor TSan passes. No suppression,
   sanitizer-disable flag or forced successful exit is used for Humble.

8. Reusing a CMake build tree with another Jazzy SDK image failed to link the
   cached Fast CDR 2.2.7 path. Rebuilding in its original SDK image passed; container
   build trees are tied to the actual dependency tuple, not only the distro name.
   `jazzy-delivery-tests.txt` retains the failed cross-image attempt.
9. New DDS-to-MCAP checks exposed host/container data loss when the container
   participants ran as root. Running the trusted container probes as the host UID
   passed all 100 actual received/written/read-back values in both distros. Distinct
   domains separate the two experiments. Shared-memory permissions are a likely
   cause, not a proven general diagnosis; failed root-run logs are retained.
10. Editing the CI helper while an earlier shell invocation was still running
    interrupted that invocation after its successful Docker image build. The final
    helper passes syntax/ShellCheck; the resulting image's runtime suite was
    executed separately. `official-humble-delivery.txt` retains the interruption.
11. The initial L2 AC-55 helper run against an older Humble image lacked the new
    `rewrite-custom` mode. Rebuilt the image; the helper then passed. Both attempts
    remain recorded; the Jazzy helper passed with its compatible image.

12. Exit-audit inspection found the preview's three Bash entries were 0775,
    inherited from the workspace by copy2. The packager now explicitly sets 0755,
    and the source entry modes were corrected. The replacement preview checks
    exact archive modes, not just executable bits. The earlier preview was moved
    to `build/phase0-delivery-superseded-mode775`; it is not the delivery artifact.

# Phase 1 implementation notes

## 2026-10-24: formal queue stress is not admitted

`tests/integration/pool_queue_stress_test.cpp` exposed an intermittent stall
when `MessageQueue` used its default constructor: two producers could remain
with acquired handle/lease pairs after 500,000 messages. The correction creates
each task queue with `max_active_topics` explicit producer slots and creates the
stress queue with its four explicit producer slots. Repeated one-million-message
runs subsequently completed. A Humble AMD64 ASan run completed on 2026-10-24
with `ASAN_OPTIONS=abort_on_error=1:detect_leaks=0`, and a Jazzy AMD64 Debug run
also completed. This must still be repeated under TSan and on ARM64 before G1
admission.

The 2026-10-24 Humble AMD64 TSan attempt built the stress target but terminated
before test execution with `FATAL: ThreadSanitizer: unexpected memory mapping`.
It produced no project race report and is recorded as an environment-limited
TSan run, not a PASS.

## 2026-10-24: dynamic GenericSubscription lifecycle

The Coordinator integration test now performs add, remove, same-name re-add and
stop on the Recorder node's Executor. Humble and Jazzy AMD64 Debug runs each
recorded and read back 1,000 `std_msgs/msg/String` samples; Humble ASan passed
the same flow. Re-adding retained the TopicId and incremented the Topic Epoch.

Calling subscription mutation from the test main thread while Humble's Executor
was in `rmw_wait` initially produced a Fast DDS ASan crash. It is therefore not
a payload-ownership result. Topic removal now notifies both the callback group
and node guard condition before releasing the subscription. A direct-control,
1,000-message Humble Debug and ASan rerun then passed.

An external-control stress run reached a SIGSEGV at 3,000 add/remove cycles
when it directly created or released `GenericSubscription` entities while the
Executor was running. TopicManager now invokes add, remove and task-clear work
through one-shot Node-Executor timers and waits for their terminal result.
Timed stop has a separate Executor-local cleanup path so it does not wait for
itself. The Humble AMD64 Debug 3,000-cycle external-control test now passes.
Humble and Jazzy AMD64 Debug each passed the 3,000-cycle external-control run.
TSan and ARM64 still need their own evidence.

## 2026-10-24: Timed mode smoke test

The Coordinator integration test constructs a separate timed-mode Coordinator,
starts a 100 ms task, waits for its Executor timer to stop it and checks the
committed manifest. The flow passed in Humble and Jazzy AMD64 Debug containers.
It verifies timer-driven stop only; elapsed-state accounting and long-duration
timing accuracy remain unverified.

## 2026-10-24: Writer-thread drain boundary

Stop no longer dequeues messages from its caller thread and posts one Writer
request per message. It closes ingress and subscriptions, then asks the single
Writer thread to drain the task queue before closing the rosbag2 Writer. This
preserves Writer ownership of every `WriterAdapter::write()` call and provides a
reusable data-drain boundary for future segment rotation. Humble and Jazzy
1,000-message Coordinator readback runs passed after this change.

## 2026-10-24: Rolling segment rotation

Rolling mode now closes ingress, waits for callback producers, drains the queue
on the Writer thread, closes the current Bag, opens the next independently
readable Bag and re-registers active topics before reopening ingress. The
manifest records the former segment as COMPLETE and the successor as WRITING.
The Coordinator integration test uses a one-second interval and independently
opens both generated segments with rosbag2 Reader in Humble and Jazzy AMD64.
Retention cleanup is implemented. Paused-window behavior is covered below.

## 2026-10-24: Rolling retention cleanup

`CleanupWorker` is a bounded single-threaded filesystem worker. A Rolling
rotation records a COMPLETE segment's completion time. On a later rotation,
expired COMPLETE segments are atomically persisted as DELETING in the manifest,
queued to the worker, and changed to REMOVED by its completion callback. A
one-second retention integration test verified deletion of the first segment and
independent readback of a later segment on Humble and Jazzy AMD64. The worker has
no timeout diagnostic yet. `recover_deleting_segments()` covers restart-time
DELETING recovery. The rolling timer calls retention evaluation after each tick,
including while `PAUSED`; the Humble integration test verifies that an expired
COMPLETE segment is removed while user-paused.

## 2026-10-24: conservative unexpected-termination recovery

Startup now preserves interruption evidence rather than deleting it. Durable
`WRITING` or `FINALIZING` segments become `INCOMPLETE`; they remain on disk.
The recovery scanner groups topic event lines by logical operation and writes
`recovery.json` with `UNEXPECTED_TERMINATION` plus any PREPARED-only operations
as uncertain. DELETING recovery remains a separate idempotent operation. The
current implementation does not yet inspect MCAP Schema, Channel or messages,
so it is not a full AC-25/AC-67 recovery implementation.

## 2026-10-24: disk protection ingress gate

Coordinator now owns a timer-driven `ResourceMonitor`. `statvfs` sampling runs
outside the Coordinator mutex. A CRITICAL or UNKNOWN result closes Topic ingress
and enters a system disk PAUSED state; `resume()` rejects this state so users
cannot override the protection. The integration test forces CRITICAL using an
unattainable `min_free_gb` and passed in Humble and Jazzy AMD64. Auto-resume
now additionally requires `resume_percent`, minimum free space and
`resume_stable_sec` of consecutive safe samples. That branch lacks a controllable
disk-sample integration test. The regression now sets `resource.enabled=false`,
which verifies disk protection remains active while ordinary resource telemetry
is disabled.

## 2026-10-24: status disk fields

`RecorderStatus` now carries the latest `DiskSample` and system-pause flag.
`write_status_atomic()` serializes the disk state, bytes, percentage, timestamps
and failure count, and writes `SYSTEM_DISK` as `paused_reason` when applicable.
The production-core test verifies these concrete JSON values. Periodic publishing
to the Session runtime directory is covered by the Session runtime integration
record below.

## 2026-10-24: Session runtime and periodic status

`SessionRuntime` uses `$XDG_RUNTIME_DIR/ros2_bag/default`, creates the Session
directory with mode 0700, owns an advisory lock and PID file with mode 0600, and
generates `recorder-` plus 16 random bytes using `getrandom`. The Recorder now
writes status.json at `status.update_hz`. A Humble process smoke run observed
the JSON with the generated instance ID and confirmed PID removal after SIGINT.
UDS request handling and basic PID/lock ownership checks are implemented.
Configurable Recorder Session selection and Web ownership-change handling remain
unimplemented.

## 2026-10-24: DELETING startup recovery

Startup calls `recover_deleting_segments()` before the Recorder node is
constructed. It replays only durable DELETING intents: an absent directory is
also treated as successful, then the manifest is atomically changed to REMOVED
and the pending entry is cleared. Failures are reported to stderr while the new
Recorder starts IDLE. The production-core test creates a DELETING directory and
verifies both filesystem and manifest recovery. PREPARED and INCOMPLETE records
remain inspection-only pending full recovery policy implementation.

## 2026-10-24: CLI graph-topic start and Executor containment

The CLI accepts `start --topics /name,/other` and serializes the list in the
JSONL start request. The ControlServer resolves each name through the Recorder
node's ROS graph only after the task Writer is open. It accepts exactly one
discovered type; no type is guessed. If a supplied topic cannot be resolved or
registered, the just-created task is stopped instead of remaining partially
started. A live Humble `std_msgs/msg/String` publisher was discovered, recorded
as TopicId 1/Epoch 1, and then stopped and restarted successfully.

The same scenario exposed a real Humble Fast DDS segmentation fault in
`rmw_fastrtps_shared_cpp::__rmw_wait` when a dynamic GenericSubscription was
destroyed while four MultiThreadedExecutor workers waited. ASan supplied the
stack. `config/recorder.yaml` now uses one worker as a containment measure.
This preserves the separate Writer and control threads, but it is not evidence
that the frozen four-worker default is safe. G1 remains blocked pending an
upstream-supported fix or a reviewed architecture/risk decision.

## 2026-10-24: status snapshot enrichment

`status.json` now serializes the available Topic state, identity, expected
frequency, matched-publisher and ingress counters, plus Pool mode/capacity,
fallback and TLS-hit metrics. Coordinator status collection first copies shared
objects under its mutex and samples Budget/Pool/TopicManager after releasing it;
this avoids a Coordinator-to-TopicManager lock-order inversion with durable
topic-event writes. The same ResourceMonitor now fills Linux task-state
CPU/RSS/FD/thread and system memory/CPU-count fields. Topic actual_hz uses fixed
10ms buckets and gap becomes true after two complete low-rate windows. Writer
per-topic write counters are WriterAdapter-owned task snapshots. Removed-topic
history is bounded by `recent_removed_instances`. The same monitor starts at
Coordinator construction, so IDLE status snapshots also contain process
telemetry after the first periodic sample. Maximum-size AC-54 validation remains
incomplete.

## 2026-10-24: one status document for file and UDS

`make_status_document()` is the single schema-v1 serialization path for both
atomic `status.json` publication and ControlServer JSONL `status` responses. The
ControlServer receives the Session and recorder-instance identifiers at
construction, so its response carries the same identity and process, system,
disk, topic and freshness fields as the file snapshot. A real Humble Recorder
was queried through its UDS and returned the required fields before accepting a
normal shutdown request. This is protocol evidence only; it does not complete
AC-54 maximum-size or full product acceptance.


## 2026-10-24: cleanup-delay test seam

`CleanupWorker` now accepts an optional deletion operation. Its default remains
`std::filesystem::remove_all`; `RecordingCoordinator` forwards the optional
dependency only for controlled integration testing. The Coordinator test injects
a 35-second deletion after rolling retention has scheduled a segment and probes
`status()` while deletion is in progress. Detached Humble and Jazzy evidence
containers both completed this test with exit code 0. No claim is made that
arbitrary filesystem calls can be cancelled; actual filesystem-error injection
remains separate work.

## 2026-10-24: Snapshot implementation and recovery inspection

`SnapshotBuffer` is Writer-thread confined. It retains the original
`shared_ptr<rclcpp::SerializedMessage>` only for Topics that explicitly enable
`repeat_on_segment`; it never duplicates CDR bytes. Per-Topic message/byte
limits and `snapshot.max_total_bytes` evict the oldest eligible entries.
Segment rotation opens and registers the new Topic channels, prunes removed
epochs, then replays retained messages with `is_replayed=true`. Removing a
Topic drains accepted messages before deleting that epoch's cache. The
production-core budget/replay unit test and a Humble build passed. A Coordinator
MCAP replay assertion has been added but is not part of a post-change full CTest.

Interrupted-segment recovery now opens each retained `INCOMPLETE` segment via
the rosbag2 MCAP Reader, enumerates Topic metadata and reads available messages.
`recovery.json` records reader-open, metadata-count, message-count and reader
errors. It does not claim raw MCAP Schema/Channel closure validation.

## 2026-10-24: status and product-control completion work

The status serializer now reports configured recording mode, stable recording
ID and explicit USER, SYSTEM_DISK or SYSTEM_UNKNOWN pause source. The Web page
now exposes existing UDS Start, Add Topic and Remove Topic operations. The
Python Web protocol suite passed after the UI change; browser product acceptance
and a post-change Recorder control end-to-end run remain unexecuted.

## 2026-10-24: Timed control, QoS selection and Writer error containment

The UDS `start` request now accepts positive `duration_sec`; CLI and Web expose
it. A Recorder configured for Timed mode rejects duration-less start and uses
the existing monotonic timer only through `start_timed`. Topic add requests can
include supported `qos` fields. Explicit QoS is preserved; otherwise
TopicManager inspects current publisher endpoints before subscription creation,
selecting reliable/transient-local only when every observed publisher offers
that policy. The current implementation does not yet emit durable
`QOS_DIAGNOSTIC` events for these choices.

On a WriterAdapter write failure, the Writer thread now transitions Recorder
state to ERROR, closes callback ingress and releases future queued messages
without further Writer calls. Explicit Stop remains responsible for Writer
close and manifest finalization. Snapshot per-Topic usage is now maintained
with Writer-thread-owned iterators, so accepted messages no longer scan the
entire snapshot cache on the Writer hot path.

## 2026-10-24: asynchronous UDS operations and control-state snapshots

Accepted side-effecting UDS commands now enter a bounded `OperationRegistry` and
return `PENDING` before a dedicated serial control worker calls the
`RecordingCoordinator`. Request-id retries reuse the existing operation and
never enqueue it twice. The registry retains the terminal command result data,
so `operation_status` continues to return allocated TopicId/TopicEpoch values.
The CLI polls `operation_status` until its configured timeout; a terminal result
uses normal success/failure exits, while an unknown terminal state retains exit
code 4 and prints the query identity. `status.json` and UDS `status` now read
the same registry snapshots for `active_operations` and `last_operation`.

Focused Humble evidence covers the production-core registry/protocol test, CLI
PENDING polling with a temporary UDS, and a real containerized Recorder whose
IDLE `status` query succeeded and whose queued `pause` command reached its
expected `INVALID_STATE` terminal result. This is not yet AC-16/17/18/56
acceptance coverage under concurrent, long-running control operations.

## 2026-10-24: durable QoS selection diagnostic

Before subscription creation, TopicManager records a `QOS_DIAGNOSTIC` event
with the final reliability, durability, history and depth and whether the choice
came from explicit input, publisher adaptation, or the default. Topic event
persistence now validates and writes a JSON-object `details` field rather than
embedding untrusted text. This is evidence of the initial selection only;
Requested-Incompatible-QoS callbacks and diagnostics for publishers that join
later remain unimplemented and unverified.

## 2026-10-24: shared Stop and Shutdown terminal outcomes

The asynchronous registry now associates a newly accepted `stop` or `shutdown`
request with an existing pending operation of the same kind. Only the leader is
placed on the serial control queue; when it completes, all followers receive the
same terminal state, code, error text and result-data object under their own
operation IDs. This avoids a second Writer-close attempt and preserves a
queryable terminal state for every accepted request. The focused
production-core test covers two distinct Stop request IDs and verifies that the
follower reaches the leader's terminal data. This does not yet replace the
required concurrent Recorder integration stress for AC-38 and AC-56.

## 2026-10-24: Web pending-operation polling

The browser client now treats HTTP 202 as accepted work, extracts the UDS
operation ID, and queries it through the CSRF-protected control relay for up to
ten seconds. It displays a terminal business result when available and retains
the original PENDING document when the query cannot be completed. This has
Python gateway regression coverage and source-level browser implementation;
interactive browser acceptance remains unexecuted.

## 2026-10-24: bounded secondary errors

`RecordingManifest` and `RecorderStatus` now carry `secondary_errors`. The
Coordinator clears the list for a new task, retains at most eight entries, and
records asynchronous retention-cleanup failures there rather than replacing the
primary task error. The same list is emitted by manifest and status serializers;
recovery preserves it when rewriting DELETING or interrupted manifests. The
focused manifest serialization regression passed in `production_core`. Further
secondary sources, such as status-publication failure accounting, remain to be
connected.

## 2026-10-24: user-facing Topic QoS and replay policy

`bag_cli add-topic` now exposes the four V1 QoS fields. It requires all four
when an explicit override is requested, so a partial command cannot silently
turn off graph-based QoS adaptation. The Web Topic form has an opt-in explicit
QoS control and exposes RepeatPolicy message/byte limits for Snapshot replay.
Both use the existing UDS request schema and leave automatic QoS selection in
place until the operator explicitly chooses an override. Python CLI/Web suites
and JavaScript syntax checking passed; browser interaction remains part of later
product acceptance.

The new CLI serialization regression also corrected the command-name boundary:
user-facing `add-topic`, `remove-topic`, and `operation-status` are mapped to
the underscore-form UDS commands. Before this correction, Topic CLI requests
would be rejected by ControlServer despite using a valid payload.

## 2026-10-24: CI release-input export and candidate manifest gate

`ci-platform.sh` now exports the verified image's Recorder binary and build
manifest into `build/release-input/<distro>/<arch>/` after native tests finish.
The L2 artifact includes those inputs alongside the evidence logs. The release
packager rejects any `phase0_only` or dirty manifest. `build-manifest.py` has
an explicit `--release-candidate` mode, which requires a clean worktree and
sets `phase0_only=false`; the normal Docker/CI path remains Phase 0 only.
This prepares a later authorized four-platform aggregation step and does not
create or authorize a release artifact. Package structural tests and shell/Python
syntax checks passed.

## 2026-10-24: explicit queue overflow contract

The configured `queue.overflow_policy` is now parsed and validated. V1 only
implements `drop_newest`, so any other value fails startup instead of being
silently ignored. The focused production-core configuration regression passed.

## 2026-10-24: deterministic Writer failure injection

`WriterAdapter` now accepts an empty-by-default write override solely as a
deterministic test seam; normal construction continues to call the synchronous
rosbag2 writer. `RecordingCoordinator` can receive that seam after its existing
cleanup and disk test dependencies. The Coordinator integration scenario injects
the first write failure and asserts ERROR state, closed ingress by observing one
write attempt, per-Topic write error accounting, and a subsequent controlled
Stop/finalization. Snapshot integration verification was also corrected to read
a closed segment and to give two real CDR String payloads sufficient byte
budget. This is targeted Humble integration work; sanitizer and long-duration
writer-failure acceptance remain pending.

## 2026-10-24: lock-authoritative managed Session startup

Managed CLI startup now tests `session.lock` with a nonblocking exclusive flock
before deciding whether a prior Recorder owns the Session. `recorder.pid` is
used only to improve the conflict diagnostic. If the lock is free, stale PID and
socket entries may be removed; if it is held, the CLI refuses to start even
where the PID is missing or stale. The focused Python regression holds the lock
while placing the current PID in `recorder.pid`, confirming that lock ownership,
not PID reuse, determines `SESSION_CONFLICT`.

## 2026-10-24: independent resource sampling and cleanup timeout diagnostics

`ResourceMonitor` now owns one process-level sampling thread. Disk and process
I/O run outside the published-sample mutex; `RecordingCoordinator` reads only
`latest()` from its timer. `latest()` converts a missing, repeatedly failed, or
monotonically stale disk sample to `UNKNOWN`. Therefore a blocked `statvfs()`
cannot hold an Executor worker while preventing the Coordinator from observing
sample age and closing ingress. The synchronous start gate still samples before
opening a Writer and can reject `DISK_STATE_UNKNOWN`.

`CleanupWorker` now reports an active path exactly once after
`cleanup.warning_timeout_sec`, without trying to interrupt the filesystem call.
The Coordinator records `CLEANUP_TIMEOUT: <segment>` as a bounded secondary
error and persists it while retaining the segment in `DELETING`; deletion stays
single-threaded and recovery remains responsible for a later retry.

Recovery now appends durable `TOPIC_ADD_UNCERTAIN` or
`TOPIC_REMOVE_UNCERTAIN` events for PREPARED operations that lack a terminal
event, then records the same operation in `recovery.json`. These uncertainty
events are terminal for subsequent recovery scans, preventing duplicate
markers. This is IMPLEMENTED and covered by the current Humble
`production_core` CTest; it has not yet received the final filesystem-fault,
long-running, or cross-platform acceptance evidence.

## 2026-10-24: Writer-side generation fence

`RecordingCoordinator::write_message()` now compares every dequeued message's
`recording_generation` with the active task before calling `WriterAdapter`. A
mismatch increments the matching active Topic's
`dropped_stale_generation`, sets `GENERATION_VIOLATION`, closes ingress through
the existing writer-failure path, and does not write the stale message. Topic
runtime state is atomic, while subscription ownership and operation error text
are accessed through the runtime mutex so periodic status snapshots do not race
with add/remove or QoS event callbacks. This is IMPLEMENTED and compiles in the
current Humble build; its controlled stale-message acceptance test remains part
of the later integrated fault-injection run.

## 2026-10-24: Topic-event persistence failure containment

A `STORAGE_UNAVAILABLE` result from dynamic Topic add or remove now invokes the
Coordinator containment path. It closes ingress, clears subscriptions, drains
accepted Writer work where possible, attempts Writer closure, and forces
`ERROR` while retaining the original persistence error as `last_error`. This
implements the required safe failure direction for AC-61. A controllable
persist-event fault seam and its complete integration acceptance are still
pending the consolidated fault-injection phase.

## 2026-10-24: status nullability and Topic error shape

When Pool is disabled, every Pool metric that has no meaning is now `null`

## 2026-10-24: Session lock precedes recovery mutation

`main()` now constructs `SessionRuntime` before invoking either recovery path.
A concurrent process cannot acquire the same Session lock and then mutate old
`DELETING` or `INCOMPLETE` manifests. The recovery documentation was updated to
match the lock-authoritative CLI behavior. This is IMPLEMENTED and the current
Humble Recorder target compiles; competing-process recovery behavior remains

## 2026-10-24: safe formatter and CI image contract

`tools/format-cpp.py` previously attempted a regex/token based second pass after
`clang-format` to force argument wrapping. Nested braced JSON initializers are
valid C++ expressions but are not safely transformable by that pass; it could
rewrite source tokens. The tool now delegates formatting solely to
`clang-format` with the repository style and is verified with `--check`.
Argument layout that needs a stricter project policy must be expressed by the
formatter configuration or changed intentionally in source, never inferred by
a text rewriter.

completed, rather than looking up the obsolete `ros2-bag-phase0` tag. This is
IMPLEMENTED and has shell syntax validation; no remote CI run is claimed.

The UDS listener applies `SO_RCVTIMEO` and `SO_SNDTIMEO` to an accepted client

publication durability boundary in line with manifest replacement without
